# Game production pipeline, agent packets and evidence-qualified progress

This is an additive Foundry frontend, not a new engine, task execution service or
agent framework. The new commands live under **`net foundry pipeline`**. The original
`ciw`/`net`, Session, experiment DAG, production workers, gates and game-owned reducer
remain unchanged. Existing `net foundry compile/run/inspect/report/export` still work.

## What this implements

The installed blueprint contains **60 work packages across 10 stages**, each with a
responsible discipline, explicit prerequisites, acceptance requirements and a proposed
division between deterministic automation, agent-assisted work and human-led decisions.
It is **our authored AAA-style breakdown**, informed by public development examples,
not Ubisoft's confidential schedule, staffing allocation or a measured replacement ratio.

The full chronological list is generated by `pipeline report`. Stages organize the
report; dependency edges determine readiness. Technical art and QA begin during
preproduction, visual/audio targets develop alongside gameplay, and performance work
starts before beta. This is not a mandate to finish every mechanic before drawing art.

| Stage | Six work packages |
|---|---|
| Definition | Vision; core loop; historical scope; rights; scope/budget; platform/input targets |
| Foundation | Runtime bindings; reproducible build; save contracts; movement; combat; telemetry |
| Prototypes | Traversal; paired combat; riding; companions; interaction access; existing water-domain qualification |
| Vertical slice | Connected journey; art target; audio target; historical review; human playtest; expansion decision |
| Tooling | Asset contracts; Blender export; collision/LOD; mission checks; localization contracts; second-unit repeatability |
| Content | World cells; settlements; props/materials; rigs/costume; missions/dialogue; content review |
| Systems | Economy/custody; recruitment/pay; workshop chain; named training; political memory; integrated progression |
| Alpha | Campaign assembly; migration; soak tests; accessibility; localization; completeness review |
| Beta | CPU; GPU; memory/streaming; devices; regression matrix; quality decision |
| Release preparation | Final rights; packaging; external certification; candidate freeze; human release decision; repair triage |

**Implemented automation is not inferred from a task label.** Only `water-domain`
is bound to an executable recipe in this increment. Its existing primary and independent
regression use `1792.water-round.v1`. Other tasks support scoped candidate packets,
change checks, dependency tracking and explicit artifact reviews, but no new Blender,
localization, mocap, texture, build-farm or coding-model worker is silently registered.

## Install and inspect

Use the feature branch containing this increment and a source checkout of the 1792
Foundry adapter. The native qualification uses game commit
`2bb8a16e63716d54de2d4e97daabc4671d3e07f4` (1792 PR #30), not an arbitrary newer game
branch. Missing adapter files refuse clearly. The latest gameplay branch may not contain
this separately developed adapter. This tool neither merges nor rewrites those branches.

```sh
python -m pip install -e '.[dev]'
net foundry pipeline init --project-id 1792 --source-root ../1792/game --output-dir results/studio-plan
net foundry pipeline status results/studio-plan/project.json --source-root ../1792/game
net foundry pipeline report results/studio-plan/project.json --source-root ../1792/game --output results/ROADMAP.md
```

`init` retains an inventory of actual source bytes and executable flags. It does not
create a second game state or mark earlier work complete just because files exist.
An existing milestone can be represented by a fresh explicit review of its real artifacts.
All output destinations must be new and outside the locked source/candidate tree.

## Agent work packet: a bounded assignment, not a prompt with unlimited authority

```sh
net foundry pipeline packet results/studio-plan/project.json --source-root ../1792/game \
  --task water-domain --assignee local-qa-host --context territory/water_round_rules.gd \
  --output-dir results/water-packet
```

This emits `packet.json` plus an `AGENT_TASK.md` instruction sheet. The packet records
its task and blueprint identities, exact baseline inventory, selected UTF-8 context,
operator-selected write paths, changed-byte budget and unchanged acceptance requirement.
Context is untrusted project data, not instructions that may override the work contract.
The native water qualification packet is read-only.

For candidate-authoring tasks, the operator may supply up to 32 exact `--allow-write`
paths. Tasks whose prerequisites are unresolved cannot be issued by the CLI. A human-led
task can have an agent propose a candidate, but that does not remove its human review.
The external host must operate in a separate assigned worktree/copy. No host account,
model API, paid inference budget or long-running agent is provisioned by these commands.

After a candidate is returned:

```sh
net foundry pipeline check results/studio-plan/project.json --packet results/water-packet/packet.json \
  --packet-id sha256:OPERATOR_RETAINED_PACKET_ID --candidate-root ../candidate/game \
  --output results/candidate-scope.json
```

Copy the exact `record_digest` from packet issuance into the trusted host configuration.
Do not accept a replacement ID supplied with an edited candidate packet. The checker
refuses a different packet identity and compares all selected source inventory entries,
including additions, deletions, bytes and executable flags. Existing tests, schema files,
license notices, `.github`, `project.godot`, and the Foundry adapter entrypoints are protected.
New tests can be granted as new exact paths; original acceptance cannot be weakened.

A result of **`scope_passed` means only the candidate stayed within the file contract**.
It does not compile, execute, merge, accept or prove correctness of the candidate.
Unchanged input also passes scope; it does not earn a completed task. Future code
acceptance must use a new explicit source revision and appropriate trusted tests.

`conflicts PROJECT --packet A/packet.json --packet B/packet.json` reports write/write
and write/read conflicts. Packets lock all inventory inputs, so this deliberately errs
on the conservative side. Independent work can be generated in isolated workspaces,
but integration conflicts require rebase and requalification. This is not a concurrent
worker pool, workspace allocator, OS lock, remote lease or crash-recovery mechanism.
The separately developed source-selection/MCP branch remains separate; this increment
does not pretend it is merged or expose new MCP tools automatically.

## Real work uses the original production controller

```sh
net foundry pipeline run results/studio-plan/project.json --task water-domain \
  --source-root ../1792/game --godot /absolute/path/to/godot \
  --godot-sha256 sha256:YOUR_VERIFIED_EXECUTABLE_DIGEST --output-dir results/water-run
```

The operator supplies the executable, never a saved task or model. Its SHA256 refers
to the actual binary, not the release ZIP. Bind only trusted code and executables.
This adapter uses a disposable directory, **not an OS or network sandbox**.

The default is the existing one-trip candidate, predeclared two-trip correction, then
fresh-process regression. The operation budget covers every possible attempt before
dispatch. `--no-repair` demonstrates exhaustion; `--candidate-trips 2` begins with the
complete candidate. Wrong source bytes, missing bindings, invalid parameters and
insufficient operation budget refuse. Unbound tasks do not launch invented workers.

The `production/` child contains the original Session, recording/execution/result files,
plan, bindings and acceptance receipts. `task-run.json` links that original production
occurrence to the blueprint task; it creates **no second execution or proof identity**.
The game owns its domain state, clock, save and observations. NET owns orchestration
and independent checking of the declared domain contract.

## Evidence changes progress; a producer's PASS does not

```sh
net foundry pipeline status results/studio-plan/project.json --source-root ../1792/game \
  --evidence water-domain=results/water-run
net foundry pipeline report results/studio-plan/project.json --source-root ../1792/game \
  --evidence water-domain=results/water-run --output results/QUALIFIED_ROADMAP.md
net foundry pipeline impact results/studio-plan/project.json --source-root ../1792/game
```

Native inspection reopens the original production history and recomputes fixed gates
without launching Godot. Both the primary and dependent regression must be accepted,
and the native source/provider/recipe must match the locked task. A test double, a
worker-authored success flag, or a successful primary without its regression is not
sufficient. Only the water-domain task advances; no vertical slice, complete game or
rendering capability is inferred from its domain fixtures.

Source changes invalidate affected evidence and dependent work. The native recipe
watches its eleven exact input modules. Other work packages currently use conservative
whole-inventory watches: changing unrelated code can require more re-review than strictly
necessary. This is a known bounded policy, not a sophisticated semantic dependency index.
A newly pinned project is an explicit new declaration; there is no silent source rebase.

Evidence for tasks whose prerequisites are blocked is explicitly marked **not inspected**;
status does not claim integrity for an unread path. Artifacts are bound to the exact
prerequisite evidence identities. Replacing an approved predecessor review makes an old
child review stale, rather than treating all reviews of that task name as equivalent.

## Human review is a separate, explicit record

```sh
net foundry pipeline review results/studio-plan/project.json --source-root ../1792/game \
  --task vision --artifact-root ./reviewed-design-artifacts --producer author-name \
  --reviewer reviewer-name --decision approved --output-dir results/vision-review
net foundry pipeline status results/studio-plan/project.json --source-root ../1792/game \
  --evidence vision=results/vision-review --evidence water-domain=results/water-run
```

The review command snapshots the selected ordinary artifact files and records a decision
against the task's acceptance requirement. It requires a different **declared** producer
and reviewer label, but **does not authenticate those people or establish that a human
actually performed the review**. This is a local operator-attestation boundary, not IAM,
a signature, objective proof of quality, or a secure multi-user authorization service.
Treat the operator profile and original packet/review storage as trusted control inputs.

Native gate work cannot be approved through this manual-review route. Conversely,
automation cannot provide a human playtest, artistic judgment or platform certification.
Reviews of such tasks are attestations supported by retained artifacts, not technical
validation fabricated by the tool. All reports retain `release_authorized: false`.
Even a fully reviewed planning graph does not deploy, upload, merge or publish a build.

## Measured output and deliberate limits

Reports distinguish machine-checked tasks, operator-attested tasks, unresolved work,
original native attempts, rejected attempts and captured native wall time. Human hours,
model cost and accepted playable minutes remain null until independently measured.
Task count is neither percent of game completion nor studio-equivalent productivity.
Failed/held/refused original production attempts remain retained; scheduling never
weakens checks or creates unlimited repair loops to achieve a green report.

File snapshots are bounded to 1,024 files, 2 MiB/file and 32 MiB total. Context is at most
32 text files, 64 KiB/file and 512 KiB total; writes are exact paths and at most 512 KiB
of replacement/addition bytes (not textual diff length). These limits target a selected
source/work package, **not a future AAA binary-asset depot**. Use bounded workcell/source
exports and preserve original data in their owning repositories. Broad depot manifests,
streamed assets and per-asset incremental qualification remain future work.

`.git`, `.godot`, Python bytecode and pytest caches are explicitly excluded. Other
symlinks, nonregular files, hardlinks, case-colliding filenames, path escapes and known
secret-bearing paths refuse. This is not complete secret discovery or race-proof
filesystem isolation. Inputs are assumed to be operator-trusted, quiescent checkouts;
permissions, code safety and process containment belong to the external execution host.
Executable flag comparison is filesystem/platform specific. No cross-platform byte-for-
byte directory identity, crash resume, cloud scheduler, remote worker authentication,
automatic issue creation, model self-approval or release automation is claimed.

No game source, commercial artwork, voices, historical book scans or engine binaries
are vendored into the new NET modules or wheel. Existing project licenses and ownership
boundaries stay in force. 1792 remains the first workload; Garibaldi can reuse the work
contracts without inheriting its game state. This does not change game narrative scope.

## Verification

```sh
python -m pytest -q tests/test_foundry_pipeline.py tests/test_foundry.py tests/test_production.py \
  tests/test_game_trace.py tests/test_game_session.py tests/test_game_retention.py \
  tests/test_control_plane.py tests/test_interactive_contract.py tests/test_interactive_session.py
python scripts/check_foundry_pipeline.py --godot /absolute/path/to/godot \
  --game-root ../1792/game --output-dir results/pipeline-native-qualification
```

Unit tests are separate from the native campaign. The latter executes baseline,
fail/correct/regression and exhausted-repair campaigns (six native attempts), reopens
all three offline with process creation forbidden, exercises candidate scope refusal
and source-drift invalidation, and checks unchanged original source. Generated candidate
notes are explicit test fixtures, not model-generated output. The report does not count
assertions over individual retained files as distinct gameplay scenarios.

The dedicated workflow tests source and installed-wheel imports on Linux/Windows,
then uses pinned Godot and game source on Linux. Exact source, wheel, JUnit and native
observations are retained. A workflow definition is not evidence of a successful run;
inspect the actual named run for the candidate revision.
